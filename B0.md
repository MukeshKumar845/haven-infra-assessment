# B0 — The `count` trap

What does `terraform plan` show when a middle landlord account is removed from the list? Why is
that dangerous here? What's the fix?

With `count`, Terraform identifies each bucket by its list position. Removing `la-002` from the
middle changes which landlord account occupies later indexes. Reproducing the plan against the
seeded state with `la-002` removed showed that `aws_s3_bucket.landlord_media[1]` and `[2]` must
be replaced: their bucket names shift from `haven-media-la-002` to `haven-media-la-003`, and
from `haven-media-la-003` to `haven-media-la-004`. Index `[3]` is now out of range and is
destroyed. The full plan also includes unrelated creates because the seeded state contains only
the four landlord buckets.

This is dangerous because a position is not a stable identity. Terraform can replace or destroy
buckets that belong to accounts that were not removed, disrupting access to their media. S3
bucket names force replacement, so this is not just a harmless index change. The bucket resource
does not enable `force_destroy`: deleting a non-empty bucket may fail at apply time, while
enabling `force_destroy` would allow its objects to be deleted.

Use `for_each` keyed by stable landlord account IDs instead, for example
`for_each = toset(var.landlord_accounts)`, with `each.key` in the bucket name and
`landlord_account_id` tag. The resource addresses then use the account ID rather than a list
position. When migrating existing state from `count`, add `moved` blocks (or use `terraform
state mv`) to map each existing numeric address to its account-ID key before applying, so the
migration itself does not recreate the buckets.
